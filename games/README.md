# Jev 打游戏实测记录：GridWorld、国际象棋、实时循环

> **证据等级：实测。** 2026-09-20，全部经 OpenRouter `POST /api/v1/systemone`，模型快照 `typesafe/jev-1.13-20260917`，约 **1,080 次真实请求、累计 $0.10**；定稿后又分两轮用约 100 次请求、$0.04 复核了下面几张表的关键行，复跑结果一并标在表下。中国象棋是后补的初探，另用约 50 次请求、不到 $0.003。网页对弈版（第六节）是 2026-09-21 至 22 日凌晨补做的，连调试约 790 次请求、不到 $0.04；第六节的问法对比是 2026-09-22 补的，约 1,180 次请求（含一轮预跑）、约 $0.055。
> 起因是把 用来打游戏（文献版，未收录本仓库） 里的说法逐条拿去跑。凡本文与那份文献冲突，以本文为准；那边已在原处加了校注。
> **未覆盖：** 官方 Doom、真实 Wikipedia 上的 Wikiracing、Elo 级别的棋力评测、官方直连、其他快照。
> 复现脚本：`exp_game_grid.py`、`exp_game_objective.py`、`exp_game_probe.py`、`exp_game_rate.py`、`exp_game_scale.py`、`exp_game_chess.py`、`exp_game_chess_prompt.py`、`play_chess_check.py`、`exp_game_xiangqi.py`、`integration/exp_ctx_rule.py`。

## 先给十一条结论

1. **循环本身几十行就能跑通，但它是一步贪心策略，不是规划器。** 5×5 GridWorld、状态给得最规整的那一臂 12 局：7 局到终点，其中 6 局走的正好是最短路（8 步）；剩下 5 局**全都是在原地打转到 18 步上限**——两局严格在两个格子之间来回（18 步只踩过 2 个格子），另外三局在四到七个格子里兜圈，一局都不是踩死的。它不会回溯。
2. **决定成败的是状态适配器，不是提问措辞。** 同一个模型、同一组动作、同一句目标，只换状态的给法：适配器把四个方向的通行情况算好（JSON）→ **156 步 0 次非法动作、7/12 通关**；只给一张 ASCII 地图让它自己看 → **98 步里 27 步撞墙（28%）、12 局有 7 局撞死在敌人格**；在 JSON 基础上再加一个"每个方向已经去过几次"的计数 → **10/12 通关**。一个纯记账字段，换来三局。
3. **用自然语言换目标，行为真的跟着换**——但只在目标是"某个地点"时靠得住。同一张图只改 objective 那一句：去终点 3/3（8 步最短路）、主动走到敌人格 3/3、去左下角 3/3，而"尽可能远离敌人并保持最大距离"只有 1/3。
4. **只读 `choice` 会漏掉它已经做出的判断。** 血量 8、弹药 2、敌人贴到 1.2 米那一帧，动作仍然是 shoot（0.47），retreat 这个动作只有 0.07；但同一次请求里 threat 从 1.27 升到 2.13、retreat 的是非判断从 0.32 升到 0.61。想让 Agent 会怕，得自己读后两个答案。
5. **状态模糊时概率不会变分散**（文献预期反了）。左右通行度 5.0 vs 4.9 这种几乎打平的局面，它把 strafe_left 给到 0.16、strafe_right 给到 0.03，熵比基线还低。"分布平坦 = 它没把握"这个直觉在 Jev 上不成立。
6. **一次请求问 900 个问题也照样答完**（那次计费 64,537 token，再多就撞整请求 64K 的墙）；300 个问题 1.71 秒答完、平均每个判断 5.7 毫秒，300 题以内没见过错题。**但题数上到 500、900 就会漏几个，而且漏的有规律**：错的全是方位贴着判据边界的题（问"是否在 180–360 度之间"，答错的方位是 168 度和 175 度），离边界远的一个没错；而且错答不都是犹豫，有的给到 0.9 以上的把握。**实测范围内没碰到题数上限，先撞的是 token 墙（1,000 题报 token 超限）；真正的风险是贴着判据边缘的那些判断——题一多，这种题的绝对数量也跟着涨。**（原文写的是"问题数没有独立上限，天花板是 token"；token 墙挡在前面，更多题数有没有单独的上限测不到。） 输出不计费，多问的钱只花在问题文本上。
7. **候选项从 2 个涨到 255 个，延迟看不出增长**（八个档位的中位都落在 1.06–1.44 秒，两次跑的排序还互相打架），代价只有输入 token（377 → 6,597）。正确项放在列表开头、中间、末尾都 3/3 选中，没有位置偏好。256 项报 400。超过 255 只能两阶段：510 项拆成 255+255 并发选优再终选，3 次请求、2.6 秒。
8. **串行 while 循环最多 0.9 Hz。** 按这条路约 1 秒的延迟，要到官方 Doom 说的 10 次/秒，必须让请求重叠飞行：固定每 100 毫秒发一帧，50 帧全部成功，但峰值有 **14 个请求同时在飞**，而且**每个决策回来时世界已经走过约 11 个 tick**（最坏 19.6 个）。官方演示怎么调度没公开。
9. **实时成本比文献表里那行低一个档。** 一个像样的 Doom 式状态（两个敌人、四向通行度、最近事件、走过的格子）实测 **726 token/帧**，10 Hz 是 **$1.10/小时**，不是 $7。$7 那行反推出来每帧要 4,630 token。
10. **象棋：战术题极准，位置判断很弱。** 一步杀 10/10，概率 0.91–0.99、confidence 0.90–0.98（全专题见过的最高值；这组问题里提示了"这里存在一步将死的机会"，不提示也是 40/40，只是 confidence 中位降到 0.68）；对随机走子 4 局，两局将死、两局到 60 手时净赚 12–13 个子。但按两层物质搜索评判，最佳着法只中 **6/12**、**平均每步亏 1.83 个子**。每局 $0.0012、纯等待 25 秒。问题里叫它"以最终赢下这盘棋为目标"或具体提醒"别被白吃"，送子没有减少（三种问法都是 104 步里送 32–37 次，和同一问法问两次的出入差不多）。
11. **换成中国象棋（初探），同一套代码基本不会下。** 一步杀 32 次只中 2 次（国际象棋 10/10），confidence 只有 0.06–0.43。怪的是它**规则背得出来**：不给棋盘只问规则，蹇马腿、炮架、兵过河、塞象眼、对脸将全答对，把握都在 0.9 以上；**可同样这几条一落到具体局面上，8 题只对 1～3 题，概率全挤在 0.43–0.61**。和第一节 ASCII 地图撞墙是同一个毛病——它看不清盘面上的几何关系。

## 一、GridWorld：状态怎么给，决定它会不会玩

6 张 5×5 地图，玩家、终点、静止敌人、三到四面墙。每一帧只问一个 choice，**五个动作恒定全给**（上下左右等待），非法方向不从候选里删——这样"会不会挑非法动作"才是可测的。踩到敌人格判死，18 步未到终点判超时。每图每臂跑 2 局。

| 状态给法 | 到终点 | 踩敌人 | 走到 18 步上限 | 非法动作 | 最高概率中位 | confidence 中位 | 每帧输入 |
|---|---:|---:|---:|---:|---:|---:|---:|
| **JSON，适配器算好四个方向** | **7/12** | 0 | 5 | **0 / 156** | 0.69 | 0.62 | 537 tok |
| ASCII 地图，让它自己看图 | 2/12 | 7 | 3 | 27 / 98（28%） | 0.47 | 0.33 | 541 tok |
| **JSON + 每个方向去过几次** | **10/12** | 0 | 2 | 2 / 148 | 0.67 | 0.59 | 640 tok |

三点值得单独说：

**① 空间推理别交给它。** ASCII 那一臂的输入 token 和 JSON 几乎一样多（541 vs 537），换来的是 28% 的动作打在墙上、7 局撞死。它连"S 右边那格是 #"都不稳。文献里"最值得投入时间的不是 prompt，而是 State Adapter"这句，实测强度比原文写得还高。

**② 失败模式都是在原地打转，不是乱走。** 最干脆的是地图 6：玩家在 (4,4)、终点在 (0,0)，往上和往左都能缩短距离，但 (3,4) 是个死胡同（上面是墙、左边是墙、右边出界）。

```text
在 [4,4] 选 up    (up=0.78 left=0.22, conf 0.71)  → 进了死胡同
在 [3,4] 选 down  (down=0.84 up=0.08, conf 0.80)  → 只能退回来
在 [4,4] 选 up    (up=0.75 left=0.24, conf 0.68)  → 又进去
在 [3,4] 选 down  (down=0.66 up=0.25, conf 0.57)  → 又退回来  …直到 18 步用完
```

`recent_moves` 字段里明明写着刚刚走过 up、down，它照样接着 up：这一局 18 步只踩过 (4,4) 和 (3,4) 两个格子，confidence 全程 0.50–0.80，一点"我在绕圈"的迹象都没有。另外三局超时兜的圈大一点（在 4–7 个格子之间转），但同样回不到正路。**贪心一步的策略不会因为你把历史塞进 state 就学会回溯。**（ASCII 那一臂的 3 局超时不是这种打转，是在 6–9 个格子里乱走加撞墙——那是看不懂图，不是回不了头。）

**③ 但一个记账字段能解开大部分死循环。** 第三臂只多了 `neighbors.<方向>.times_already_visited` 和一句"别在两个格子之间来回绕圈"。地图 2 的对照最干净——两臂前六步一模一样（右、左、右、左、下、下），到第七步分叉：

```text
JSON          … (2,0)→up    → 又绕回去，18 步超时
JSON+访问计数  … (2,0)→right → 继续绕过敌人，15 步通关
```

代价是每帧多 100 token（+19%）。**需要绕路的地图，去重记账比换措辞有用得多。**

但它也不是万能的。地图 6 里，访问计数确实让它第三步就跳出了 (4,4)↔(3,4) 的死胡同（left 0.57 压过 up 0.42），一路走到终点旁边的 (0,2)；可 (0,1) 是墙，剩下唯一的路是**先往下退两行、横过去再上来**，于是它又在 (0,2)、(0,3)、(1,2) 这三个格子之间来回到步数用完（另一局绕得开一点，探到 (0,4) 又折回来，同样没走出去）。**"必须先远离目标"这种局面要真正的搜索，自己写 BFS 比喂字段省事。**

**④ 同一个请求体，答案会变。** 这一组换到第四节那个 Doom 式状态上测（八个动作，信号更丰富）：完全相同的请求连发 10 次，每个动作的概率极差 0.02–0.07，排头的 forward 和 shoot 本来就贴着（0.28–0.34 对 0.22–0.29）：第一轮 10 次里有 1 次 argmax 从 forward 翻成 shoot，定稿后再连发 10 次则 10 次都是 forward——**翻转是偶发的，但确实会发生**。**单帧的抖动很小，但循环会把它放大**：同图同臂两局按步序号对齐、位置和动作都相同才算一致，一致率 JSON 64%、ASCII 41%、JSON+计数 73%（注意这是轨迹级指标——一旦某一步分叉，后面全算不同，所以它反映的是"轨迹会不会跑偏"，不是"每次判断有三成不一样"）。**游戏 Agent 的回放不可复现，benchmark 要按随机过程处理、多跑几局取分布。**

## 二、换一句目标，行为会不会变

同一张图（玩家 (0,0)、终点 (4,4)、敌人 (2,2)）、同一套动作、同一组状态字段，**只改 objective 那一句话**，每个目标跑 3 局、上限 12 步：

| objective 写成 | 达成 | 平均步数 | 轨迹在做什么 |
|---|---:|---:|---|
| 尽快走到终点，别踩敌人 | 3/3 | 8.0 | 走最短路，绕开敌人 |
| 唯一目标是走到敌人那一格 | 3/3 | 4.7 | 直奔敌人，主动送死 |
| 唯一目标是走到左下角 | 3/3 | 4.0 | 一路向下，完全无视终点 |
| 唯一目标是尽可能远离敌人、保持最大距离 | 1/3 | 12.0 | 两局沿边走到底排，在离敌人 2～3 格处来回震荡 |

（前三行的"达成"是走到了那个格子；最后一行的判定标准是 12 步走完时与敌人的距离不小于起始的 4 格。**注意这一行连那个 1/3 都是虚的**：达成的那局全程在起点附近打转，靠起点本来就离敌人 4 格过的关；另外两局反而越"逃"越近，最后在离敌人 2～3 格的地方来回。）

**"去某个地点"它执行得很好，"最大化某个量"它做不到。** 同一个模型，前三行是 9/9，最后一行 1/3。要表达"保持距离"这类持续目标，得自己把它翻译成地点或阈值（例如把"最远的安全格"算出来当 goal），别指望一句形容词。

固定状态那组也测了同一件事，结论一致但更细：同一帧把 objective 从 `reach_exit` 换成 `kill_all`，**众数动作不变**（都是 shoot），但 shoot 的概率从 0.46 跳到 0.88、confidence 从 0.38 升到 0.87、熵从 2.15 掉到 0.74。**目标改变的是概率质量，不一定改变 argmax**——只看 `choice` 字段的人会以为目标没起作用。

## 三、文献建议的第一轮测试集，逐项跑完

Doom 式结构化状态（health、ammo、objective、可见敌人的方位与距离、前/左/右三向通行度、最近受伤方向、出口距离），八个动作，一次请求同时问 action（choice）、threat（score 四档）、retreat（noul），每个场景 5 次：

| 场景 | 文献预期 | 实测 | 判定 |
|---|---|---|:--|
| 基线 | — | shoot 0.49、熵 2.12（八选项满熵 3.0）、conf 0.39、threat 1.27、retreat 0.32 | 基准 |
| 血量 8 + 敌人贴身 | retreat 概率提高 | threat **1.27→2.13**、retreat **0.32→0.61**；但动作仍是 shoot，retreat 动作只有 0.07 | **半对** |
| 高血量 + 弹药足 + 敌人近 | shoot 概率提高 | shoot 0.49→0.57，熵 2.12→1.42，conf 0.39→0.53 | 对 |
| 正前方封死（0.2 米） | forward 应降低 | forward **0.22→0.07** | 对 |
| `kill_all` ↔ `reach_exit` | 行为应改变 | shoot 0.46→0.88、conf 0.38→0.87；argmax 不变 | 对（在分布上） |
| 左右信息近似 | 概率应更分散 | 熵 1.99 **低于**基线 2.12；strafe_left 0.16 vs strafe_right 0.03 | **反了** |
| （同上一行）| — | 而且它选了 forward（0.59），可那个方向只剩 0.3 米 | 不管合法性 |
| 删掉敌人距离 | 不确定性增加 | action conf 0.39→0.30、5 次里 1 次 argmax 翻转；但 threat 的 confidence 反而从 0.74 升到 0.85 | **弱** |

两条要划重点：

**"血量 8 还在开枪"不是模型笨，是问题设计的责任。** 它在同一次请求里已经明确告诉你"威胁 2.13 / 该撤退 0.61"，只是 action 这个问题的候选里 retreat 竞争不过 shoot。**正确接法是让代码读 threat 和 retreat，再决定要不要采纳 action**——文献里"游戏策略仍然写在代码里，Jev 只把模糊判断变成概率"这句，实测支持。

**别用分布平不平来判断它有没有把握。** 左右几乎打平时它照样把概率压到一边；反过来，基线这种信息充足的局面熵却有 2.12。真正随信息量变化的是 `confidence`（0.30–0.53 之间动），但幅度小、而且 score 的 confidence 会往反方向走。想知道"该不该信这一帧"，只能自己拿标注数据定阈值。

两点关于这张表的说明，免得被当成比它本身更强的证据：**"左右信息近似"那一格不是只动了左右两个数**——它同时去掉了可见敌人和出口信息、正前方也压到 0.3 米，这样才逼出"只能在左右之间选"的局面；要看的是分布散不散，这一点不受影响，但别把它读成单变量实验。另外**"基线"和"目标=reach_exit"其实是同一个状态测了两遍**，shoot 一个 0.49 一个 0.46——这 0.03 就是同状态的跑间抖动，正好给上一节那条抖动结论做个旁证。还有一个口径要说明：表里**单个动作的概率取的是五次中的第一次**（只有这一次存下了完整分布），而熵、置信、威胁分、撤退概率是**五次均值**；两者差在 ±0.03 以内，也就是同状态的抖动量级。

顺带一条给这类循环算钱的人：同一帧**只问 action** 是 548 token / 1.11 秒 / $0.0000230，**问 action+threat+retreat** 是 635 token / 1.11 秒 / $0.0000267。多两个判断，延迟不变，贵 16%。（这一格复跑过两次：548 / 635 这两个 token 数一模一样，延迟一次 1.08 / 1.05 秒、一次 1.14 / 1.15 秒，同样分不出高下。）

## 四、实时性：0.9 Hz 的循环怎么变成 10 Hz

用 726 token 的 Doom 式状态（三个问题一起问）实测。（比第三节那个状态多了第二个敌人、后方通行度、最近事件和走过的格子，所以每帧从 635 token 涨到 726。）

| 打法 | 结果 |
|---|---|
| 串行 while（收到答案再发下一帧） | 15 帧 16.6 秒 → **0.90 决策/秒**；单次 中位 1.09s、p90 1.18s |
| 固定 100ms 发一帧、不等回包 | 50 帧全部成功；发送节拍达成 10.2 Hz，收完 5.91 秒；**峰值 14 个请求同时在飞**；延迟 中位 1.09s、p90 1.19s、最大 1.96s |

**所以"官方 Doom 10 次/秒"和"单次约 1 秒"并不矛盾：按这条路的延迟，10 Hz 只能靠重叠请求。** 官方演示是不是这样调度不知道：调度代码没公开，官方自报的延迟（70–500 ms）也比这里低。（原文写的是"它必然是重叠请求"，把本实验的延迟套到了官方演示上。）这也直接量化了文献里提醒的过期问题：本实验 10 Hz 下，**决策回到手里时世界已经走了 10.9 个 tick（中位；平均 11.3）**，最坏 19.6 个。文献建议的 tick ID 丢弃法，实测下来不是保险措施而是必需品；而且丢弃阈值不能按"1、2 个 tick"设，得按十几个 tick 设，否则全被丢掉。

要注意这只是 5 秒、50 次请求的短脉冲，没有触发任何限流，**不代表能持续跑一小时**。官方文档的 1,200 RPM（合 20 次/秒）在这条路上没验证过。

成本用实测 token 数重算（$0.042/M 输入、输出免费）：

| 频率 | 每帧 | 每小时输入 | Jev 成本/小时 |
|---:|---:|---:|---:|
| 1 Hz | 726 tok | 2.61M | **$0.11** |
| 5 Hz | 726 tok | 13.07M | **$0.55** |
| 10 Hz | 726 tok | 26.14M | **$1.10** |

文献那张表算法没错，但代入的 4,630 token/帧是从官方"$7/小时"反推的。**真按一个结构化 Doom 状态来写，每帧 700 token 量级就够**，10 Hz 一小时一美元出头。差的那 6 倍要么是官方 state 大得多，要么包含了别的开销。

## 五、候选项能有多少、一次能问多少

### 候选项数量（Wikiracing 那一路）

任务构造成有唯一正确答案：目标页 `Alan Turing`，候选里塞一个 `Bletchley Park`，其余全是"排球器材""巴洛克音乐术语"这类无关条目，每档 3 次。

| 候选项数 | 延迟中位 | 输入 token | 选对 | p(正确项) |
|---:|---:|---:|---:|---:|
| 2 | 1.15s | 377 | 3/3 | 1.00 |
| 16 | 1.11s | 712 | 3/3 | 1.00 |
| 64 | 1.06s | 1,843 | 3/3 | 1.00 |
| 128 | 1.11s | 3,371 | 3/3 | 1.00 |
| **255** | **1.31s** | **6,597** | 3/3 | 1.00 |

每个档位只跑 3 次，延迟中位的抖动比候选数的影响大：复跑一次同样八个档位，中位落在 1.08–1.44 秒，2 项那档反而比 128 项慢。**输入 token 则完全可复现**，两次跑每一档一个 token 都不差。

正确项放在列表首、中、尾各 3 次，全部 3/3、概率 1.00——**没有位置偏好**。注意这个任务对它太简单（干扰项语义上离得很远），**"255 项也不会选歪"只在这种难度下成立**，真实 Wikiracing 里几百个都沾点边的链接没测。

256 项确认报 `400 Too many choices. Must have at most 255 choices.`。**两阶段**（510 项 → 255+255 两块并发各选一个 → 终选）实测：第一阶段并发 1.44 秒、第二阶段 1.18 秒、**总 2.62 秒 / 3 次请求**，正确项活到最后。文献说"某些步骤会变慢"，具体就是**大约翻倍**。顺带一个实现上的坑：不含正确项的那一块照样会交回一个"胜者"（那次是 `Lighthouse history`），所以终选那一轮不能省。

> **更正记录：** 本节原来写的是"总 2.42 秒"，那一次的候选池其实只有 301 项——脚本造干扰项的生成器上限是 300，510 被悄悄截短，分块成了 255+46。修好生成器、真的跑满 510 项之后才是上面这组数字。

### 一次请求里的问题数

state 里放 k 个敌人的方位（0–360 度，7 度一档随机取），问 k 个是非题（"这个敌人的方位是否落在 180 到 360 度之间"），答案完全客观：

| 问题数 | 延迟中位 | 输入 token | 输出 token | 答错的题数 |
|---:|---:|---:|---:|---:|
| 1 | 1.07s | 342 | 21 | 0 |
| 16 | 1.09s | 1,366 | 282 | 0 |
| 128 | 1.31s | 9,231 | 2,326 | 0 |
| 300 | 1.71s | 21,553 | 5,594 | **0**（复核两跑都是 300 题全对） |
| 500 | 2.08s | 35,882 | 9,394 | **4～7**（四次复核：7、5、4、5） |
| **900** | **2.75s** | **64,537** | 16,994 | **3～4**（两次复核：4、3） |
| 1000 | — | 约 7.2 万（按 900 题比例推算） | — | 400 `max_tokens_exceeded` |

**300 个判断 1.71 秒，平均每个 5.7 毫秒，一题不错。** 实测范围内没碰到题数上限，先撞的是 token 墙（1,000 题那次报的是 `max_tokens_exceeded`）。（原文写的是"问题数本身没有上限"。）输出 token 不计费，所以这条路上你多问的只是问题文本的钱。

但**几百题的时候会漏几个，而且漏在哪很有规律**：所有答错的题，方位都贴着判据的边界——问的是"是否落在 180 到 360 度之间"，答错的那些方位是 **168 度和 175 度**，离 180 只差几度；离边界远的题一个没错。按边界题算错误率：300 题里这种题有 14 个，两跑全对；500 题里 18 个、错 4–7 个；900 题里 35 个、错 3–4 个。而且错答的方向全一致（都把 180 度以下说成在 180–360 之间），把握也不低——有几个给到 **0.9 以上**，其中一个 0.97。

所以这条便宜路的风险不是"题多了就整体变糊"——900 题的错题数并不比 500 题多，各档也只跑了两到四次，看不出随题数单调上升——而是**贴着判据边缘的判断本身就不稳**：题一多，这种边界题的绝对数量跟着涨（300 题里 14 个、900 题里 35 个），撞上的机会自然多。能钉死的只有一句：300 题以内两跑没出过错，再往上会零星漏。实用做法：要紧的判断别混在几百题里一起问，或者把判据设计成别卡在边界上。（这里不是刻意设计的陷阱：方位是 7 度一档随机取的，只差 5 度的 175 度在 900 题里出现了 23 次，把这条线踩满了。）

（表里延迟是两次调用的中位，复跑时 128 题那档跳到 1.78 秒、900 题 2.4–2.6 秒——±0.4 秒的抖动比问题数的影响还大；输入 token 则一个不差地可复现。错题数是定稿后复核重跑时逐题比对出来的：500 题那档跑了四次、900 题两次，列出的就是各次答错的题数。）

对游戏的实际含义：一个 tick 想顺便判断二十个敌人的威胁、五条路线的风险、三个目标的优先级，**全塞进同一个请求**，比拆开发省一个数量级的时间。

## 六、下棋：国际象棋能复现，中国象棋基本不会

合法着法全部由 python-chess 枚举后作为 choice 候选，criteria 的描述写 SAN，state 只放 FEN 和行棋方——和文献描述的社区做法一致。

**一步杀：10/10。** 五个局面各两次，问题末尾都加了一句"注意：这里存在一步将死的机会。"（原文漏写了这句提示），全部找到唯一的将死着法，选中概率 0.91–0.99、confidence 0.90–0.98。这是整个专题里 confidence 最高的一组数字，**说明它在强制性战术上确实知道自己知道**。2026-09-22 补测了不加提示的情况（`exp_game_chess_prompt.py`）：按网页对弈版的原问法问，这 5 个加随机对局里抽的 35 个有一步杀的局面，**40/40 全中**，confidence 中位从加提示时的 0.92 降到 0.68。提示只让它更有把握，不影响选没选中。

**两层物质搜索的最佳着法：6/12，平均每步亏 1.83 个子。** 最有代表性的一次：白方后和黑方后互相贴着，用后吃后能净赚一个后（因为黑马够不到 d5），用马吃后则会被黑马反吃白后、白忙一场。它选了马吃后，两次都选。**而那两次它的 confidence 只有 0.16 和 0.19——全组最低。** 低置信确实对应了它的短板。

**对随机走子 4 局（Jev 执白，60 手截断）：**

| 局 | 结果 | 白方净子 | Jev 步数 | 每步延迟中位 | 每步输入 | 本局成本 |
|---:|---|---:|---:|---:|---:|---:|
| 1 | 未终局 | +13 | 30 | 0.92s | 1,114 tok | $0.00140 |
| 2 | 未终局 | +12 | 30 | 0.91s | 1,050 tok | $0.00132 |
| 3 | **1-0 将死** | +20 | 24 | 0.91s | 1,056 tok | $0.00107 |
| 4 | **1-0 将死** | +15 | 22 | 0.92s | 1,054 tok | $0.00097 |

平均每局 **$0.0012、纯等待 25 秒**。文献引用的社区数据是 **$0.0015/局、35.6 秒/局**——量级完全吻合，可以互相印证。**但那篇的 243 Elo 本文没有验证**：4 局对随机走子只能说明它明显强于随机，说不出 Elo。

把这三组放一起看，"Jev 会下棋"的准确说法是：**规则和合法性由棋库负责，它负责在已知合法着法里选一个；强制战术很准，静态局面会送子。** 对帖子和 demo 够用，对棋力评测不够。

**换个问法也改不动棋力**（2026-09-22 补测，`exp_game_chess_prompt.py`）。取网页对弈版最终测试里 Jev 面对的 98 个局面（人那边随机走子），加上面 6 个战术局面，共 104 个；在原问法后面分别加"选的时候以最终赢下这盘棋为目标"、加具体提醒"先看有没有一步就能将死对方的着法；没有的话，确认走完之后自己的子不会被对方白白吃掉"，三种问法各问两次，用上面的两层物质搜索打分。走完就被对方吃回来、比走之前少 2 分以上的送子，原问法两次是 37、32 次，以赢棋为目标 35、32 次，具体提醒 34、32 次；每步平均比最好的一步差 1.67–1.88 分。换问法让它在 104 个局面里有 20 个改选了别的着法（同一问法问两次也有 9–14 个不同），但改选的并不更好。叮嘱补不上它看不清盘面的短板。

### 在浏览器里和它下（网页对弈版）

同一套接法做成了网页：一条命令起本地服务、自动打开浏览器，人在棋盘上走，Jev 回一步，旁边列出它最看好的五步和各自的概率。棋规和棋盘在网页里（chess.js 与 cm-chessboard），本地脚本只用标准库，把网页送来的局面和合法着法按上面实验的 `ask()` 原样拼成请求（它不重新核对着法合不合法，信任本机网页）（`play_chess.py`）。key 只在本地进程里，网页拿不到。

**发出去的请求和上面实验里两层搜索、对随机走子那两组逐字节相同，所以上面的结论原样适用**（一步杀那组多带一句提示，不带提示的补测也全中，见上）。 让网页用的同一份 chess.js 随机下 200 局，31,604 个局面两边的请求体全部一致，其中被将军的 1,674 个、能升变的 1,049 个、能吃过路兵的 109 个（`play_chess_check.py`，不调 API）。这个比对抓得住错：故意改坏着法的排序，30 局里就报出 43 处不一致。再真实调用 5 个局面，两边实际发出的字节也相同，选的走法一样，概率相差不超过 0.05。

在无头 Chrome 里真走了 3 盘（人这边随机走子，两盘执白、一盘执黑，每盘最多 40 步）：Jev 共走 99 步，**页面上每步等待中位 1.10 秒，九成在 1.21 秒以内，最慢一步 1.67 秒**；每步输入 750–1,550 token，合法着法越多越长；**一盘 40 步约 $0.002**。

**偶尔有一步会卡很久。** 做这个网页前后约 790 次调用，有 3 次单次调用拖到 20 秒以上：21 秒、76 秒，还有一次等了 90 秒还没回来（后两次出在同一轮测试里）。设 timeout 挡不住：urllib 的 timeout 管的是多久没收到数据，不管总共等了多久，那次 21 秒的调用就是在 20 秒 timeout 下照样等完的。网页版因此按总时长截断：到 20 秒就断开连接、另发一次，两次都没回才报错。用假上游模拟"一直不回"和"每 5 秒来一点数据"两种卡法，都在第 20 秒断开另发、马上拿到答案。断开的那次 OpenRouter 算不算钱不知道，脚本退出时单独报这类次数。

### 换成中国象棋（初探）

同一套接法原样换过来：合法着法由 `cchess` 枚举，criteria 的描述写中文记谱（"车二平五"），state 放中国象棋 FEN 和行棋方（第二轮另加一句坐标约定），提问一字不改。这是初探，两轮共约 50 次请求；第二轮就是 `exp_game_xiangqi.py` 的原样输出，两轮结论一致。

**一步杀：32 次只中 2 次。**

| 局面 | state | 着法描述 | 第一轮 | 第二轮 | confidence |
|---|---|---|---:|---:|---:|
| 四个随机搜出的"只有一步能杀"局面 | FEN | 中文记谱 | 1/4 | 1/4 | 0.08–0.18 |
| 同上 | FEN | 坐标（"车从 h6 走到 e6"） | 0/4 | 0/4 | 0.08–0.26 |
| 双车错、马后炮，各两次 | FEN | 中文记谱 | 0/4 | 0/4 | 0.06–0.15 |
| 同上 | 子力清单（"红方车在 a8、i7"） | 中文记谱 | 0/4 | 0/4 | 0.11–0.43 |

国际象棋同样的题是 10/10、confidence 0.90–0.98（两边问题末尾都带着"这里存在一步将死的机会"）。三点值得记：**记谱写法救不了它**（中文记谱和坐标都不行）；**错得不随机**——两个教科书杀型那 16 次，同一格设置下几乎每次都选同一步错着（马后炮给 FEN 四次都选"马四进六"），多采样也没用；**给它更好读的子力清单也没有更对**，confidence 倒是有时更高（最高 0.43，给 FEN 时不超过 0.15）。

**规则：背得出来，用不到盘面上。**

| 测法 | 中国象棋 | 国际象棋 |
|---|---|---|
| 不给棋盘，只问规则本身 | 6 题错 1 题，两轮都是同一题；答对的把握 0.91–0.97 | 3/3 |
| 开局局面，4 步合法 + 4 步违规 | 8 题错 1 题，两轮都是同一题；概率 0.23–0.69 | 8/8；合法 0.89–0.94、违规 0.19–0.46 |
| 细则摆进同一个局面（蹇马腿、炮架、兵过河、对脸将、塞象眼、士走斜线） | 两轮 8 题分别只对 1 题、3 题，概率全在 0.43–0.61 | — |

最能说明问题的是两对：不看盘时，它以 0.97 的把握说"马腿被占就不能跳"，看盘时马腿明明被自己的兵占着，它两轮都判能跳（0.59、0.61）；不看盘时，它以 0.91 的把握否定"帅将可以照面"，看盘时一步走完就让帅将照面的着法，它两轮都判合法（0.57、0.58）。**规则它知道，只是判断不了具体那一格有没有子。** 它唯一真记错的规则是"士能在九宫里直走"，两轮都以 0.92 答"能"。开局那组唯一的错也是同一类：车前面隔着自己的兵，它照样判能直冲过去。

看盘本身也偏软：同一局面六个客观是非题（谁还有车、黑方是否被将军、黑方还剩几个士……），两轮一共对 11/12，错的一题是"黑将是否在中路"（0.49）；但除了"红方还有车"是 0.93–0.94，其余概率都在 0.24–0.63 之间。

**这和第一节是同一个毛病。** 让它看 ASCII 地图自己判断哪边是墙，28% 的动作撞墙；让它看棋盘自己判断马腿有没有被塞，等于抛硬币。第一节的解法是适配器把几何算好，但这里只把棋盘改写成子力清单并不够（上表最后一行）；按同样的思路推下去，适配器得替它算出每步着法的后果（是否将军、会不会被吃、是否形成杀），那时下棋的其实是棋库——**这一条是推断，没测**。

两个会绊人的坑：`cchess` 的单步合法性检查**只查每个子自己的走法，不查走完后自己的帅会不会被将**（对脸将也在这一类），完整合法要再加一道检查；它还用"帅直接吃将"这种伪着法表示对脸将，列候选时要剔掉。第一轮只剔了吃将的伪着法，候选里还混着几步走完会被将的着法（每题至多一步），正式脚本已剔除，结果不变。

> **更正记录：** 规则测试的第一版把答案写进了题干（如"马从 h1 直着走到 h2（马走直线）""它前面的 c4 有自己的兵挡着腿"），其中一题还把局面写错了（写着"中间一个子都没有"，其实隔着一个马）——那一版整版作废，表里全是改成"只说某子从哪走到哪"之后重测的。重测第一轮里，"走完帅将照面"那题起初按棋库的单步检查判成合法，查明棋库不查这一层后改判违规。

**边界：** 只有 6 个局面、两轮；随机搜出来的局面子力稀疏、不像实战，教科书杀型只有两个；没有下整局、没有做物质搜索、没有接引擎（`cchess` 自带 UCCI 和 UCI 两种引擎接口，要做棋力评判可以接皮卡鱼这类引擎，没试过）；细则每轮只摆了一个局面、8 题。

## 七、顺带纠正了一条自己的旧结论：上下文不是一道墙，是两道

问 900 个问题的那次请求计费 **64,537 input token 却正常返回**，直接撞翻了我上一轮写下的"整个请求约 32.9K 就封顶、文档说的 64K 不成立"。重测后规则很清楚——**官方文档两条都是对的，是我上一轮只往 state 里灌长文，而那种测法下两道墙正好重合在 32K**：

| 请求形状 | 每对（state + 最长问题） | 整请求 | 结果 |
|---|---:|---:|:--|
| state 32K + 1 个短问题 | ≈32K | 32,283 | ✅ |
| state 33K + 1 个短问题 | ≈33K | ~33K | ❌ |
| state 30K + **1 个 5K 长问题** | ≈35K | ~35K | ❌ 总量更小反而被拒 |
| state 15K + 3 个 10K 长问题 | ≈25K | **45,334** | ✅ 总量大得多却通过 |
| state 15K + **2 个 20K 长问题** | ≈35K | ~55K | ❌ 总量比下一行小，但那一对超了 |
| state 15K + 5 个 10K 长问题 | ≈25K | **65,380** | ✅ |
| state 5K + 30 个 2K 问题 | ≈7K | ~65,900 | ❌ |

- **`state` 加上最长的那一个 question ≤ 32,768**；
- **整个请求 ≤ 65,536**（实测 65,380 过、约 65,900 拒）。

对游戏的用处很直接：**长状态省不下来的时候，把"问题"拆多几个不会让你更早撞墙**（每个问题各自和 state 配对算），但总量仍然封在 64K。详见 [接入实测记录](../integration/README.md) 该节与 `integration/exp_ctx_rule.py`。

## 八、要动手的人，按这个顺序省事

1. **先写状态适配器，把几何、可行动作、计数都算好再发**——这一步的收益比任何提问措辞都大（0 次非法 vs 28% 非法）。
2. **一次请求把所有要判的事全问完**：动作、威胁、是否撤退、目标优先级。延迟不变，成本只多一点，最多能问到几百个。
3. **动作合法性、死循环、去重，自己在代码里兜**。它不保证合法，也不会自己跳出两格震荡；`recent_moves` 塞进 state 没用，`times_already_visited` 有用。
4. **目标写成"到哪里去"**，不要写成"尽可能最大化什么"。
5. **实时循环从第一天就按重叠请求写**，带 tick ID，丢弃阈值按十几个 tick 设，不是一两个。
6. **拿 threat / retreat 这类辅助判断当护栏**，别让 `choice` 一个字段说了算。
7. **benchmark 多跑几局取分布**：同一请求体也会翻转，单局结果不可复现。
8. **钉快照串** `typesafe/jev-1.13-20260917`。本文所有数字只在这一个快照上成立。

## 未验证与已知边界
